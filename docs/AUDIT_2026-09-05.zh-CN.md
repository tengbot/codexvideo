# CodexVideo 目标、能力与交付审计

审计日期：2026-09-05。代码基线：`5cb549c49d92863b73289f36638fab9982da025e`。

本报告只审计和提出方案，不表示下列缺陷已经修复。当前凭证、模型可用性和本地产物的观察只对本次检查有效；不等于上游最新版本调查或云端服务验证。

## 一、结论

**相对于“给网站，让普通用户在 Codex 中稳定做出值得发布的英文推广视频”，当前完成度约 60%。不是 90%，也不是从零开始。**

这里的百分比是有权重的工程判断，不是统计成功率、测试覆盖率、剩余工时或广告转化预测。主评分计算为 58.25/100，对外表述取整为约 60%，判断误差约正负 10 个百分点。

| 观察层次 | 当前判断 | 不能据此声称什么 |
| --- | --- | --- |
| 创作工具与工程零件 | 约 80%，定性判断 | 工具存在不等于每个 API 都能用，或每条路线都跑通 |
| 本地目标工作流 | 约 60%，下文加权评分 | 做过几条视频不等于新网站、新项目可稳定复现 |
| 新用户下载后开箱使用 | 约 40%，定性判断 | 当前机器配置不等于干净环境的默认体验 |
| 未来多用户 SaaS | 约 10%–20%，定性判断 | 本地 CLI 和看板不是租户、账户、队列、支付与履约系统 |
| 消费者吸引力与真实转化 | 未知 | 创意自评分、播放成功、仓库流量都不能证明转化效果 |

核心问题不是“还没有收集足够多的开源项目”，而是：**已经有很多局部能力，但共同的营销策略、内容形式、运行状态和验收证据还没有统一起来。**

## 二、历史意图还原

本次核对了当前会话从 6 月到 9 月的可读取记录。119 条用户角色记录中，25 条是明显的环境、指令或中断信息，其余约 94 条是实际交互消息。这个数字不是 119 轮完整讨论。以下只保留产品需求，不公开原始聊天记录。

### 真正要做的产品

不是通用剪辑器，也不是“读网页文案加几张截图”的模板工具，而是一个 **Codex 原生的、以消费者需求为起点的视频制作工作台**。

目标链路：

```text
网站 / 产品说明 / 现有素材
  -> 核实产品能做什么、不能做什么
  -> 找到消费者真实情境、搜索意图、痛点和反对理由
  -> 提出 20–50 个痛点，产出约 10 个差异化脚本，推荐 5 个
  -> 每条只解决一个需求：前三秒痛点 -> 解决方案 -> 可见证据 -> CTA
  -> 选择内容形式与风格，而不是重写整套策略
  -> 匹配素材、英文声音、镜头、字幕、音乐和音效
  -> 先预览、审核，再完整渲染
  -> 技术检查 + 内容检查 + 真人观看确认
  -> 批量变体、多比例导出、记录表现，再改进下一批
```

### 必须保留的要求

| 要求 | 我的理解 | 交付时应当如何验收 |
| --- | --- | --- |
| 消费者视角 | 讲观众此刻想解决的问题，不替商家念功能表 | 能指出具体人、具体情境、具体损失或期待 |
| 前三秒 | 尽早让观众听懂痛点，不把开场浪费在品牌介绍 | 实际配音和首个画面在 3 秒内表达同一痛点 |
| 先脚本后素材 | 先决定论点与证据，再找素材 | 每个镜头对应脚本句子、用途和证据来源 |
| 专业英语声音 | 面向英文市场；自然口语、节奏、发音和音色都要合格 | 试听通过，不以系统朗读或低级替代品冒充正式配音 |
| 无脸视频 | 无出镜主持人的旁白叙事，可用相关 B-roll、产品实录和生成画面 | 不是静态网页截图轮播；画面随叙事推进 |
| 双人 AI 播客 | 两位稳定角色，以提问、质疑、解释和证明推动对话 | 有自然轮次、口型、反应镜头和一致录音棚，不是两张照片轮流亮起 |
| 产品质感 | 镜头、转场、字体、音效共同服务内容 | 展示真实结果或使用过程，动效不能遮住产品证据 |
| 批量生产 | 先有高质量母版，再控制变量扩展 | 记录哪个痛点、Hook、主体、CTA 被改变，失败只重跑必要部分 |
| 本地先跑顺 | 先把自身产品制作流程变可靠，再包装 SaaS | 不需要每次靠长会话临时补脚本、补文件、猜路径 |
| 轻量、可控成本 | 少装东西，不让电脑过热，不静默切付费模型 | 依赖按需安装，限制并发，预览先行，费用和供应商明确 |
| 开源融合 | 把可复用能力真正纳入本地工具、契约和测试 | 能指出源码落点、许可证与调用证据，不把“看过”说成“集成了” |
| 可公开交付 | 别人下载仓库后 Codex 能理解任务、边界和下一步 | 文档一致、样例可复现、配置可诊断、交付可验证 |

这些需求不是频繁变更目标：无脸、播客、产品动效是同一条营销生产链上的不同内容形式。换脸、直播切片、3D 等是可选分支，不应挤占两条主线的验收工作。

“批量”也不等于单纯排列组合。8 个相同素材的组合，并不能替代 5 个针对不同消费者需求、各自有证据的广告创意。

## 三、当前架构究竟是什么

```text
Codex 会话：负责研究、决策、写脚本、编排工具、判断画面
  |
  +-- AGENTS.md / AGENT_GUIDE.md：入口与协作规则
  +-- codexvideo/：CLI、格式路由、项目建立、能力预检、恢复提示
  +-- config/consumer_profiles.yaml：6 种用户格式、6 种风格、provider packs
  +-- pipeline_defs/ + skills/：阶段定义和角色操作说明
  +-- schemas/artifacts/：结构化交付契约
  +-- tools/ + lib/：素材、生成、剪辑、渲染、费用、检查、状态工具
  +-- projects/<id>/：脚本、素材、checkpoint、报告和成片
  +-- Remotion / HyperFrames / FFmpeg：渲染执行层
  +-- backlot/：主要是只读生产看板
```

本次清点：132 个工具类、46 个 artifact schema、16 个 pipeline YAML（含 framework-smoke，不是 16 条已验证生产线），其中 `skills/pipelines/` 有 139 份 Markdown 阶段说明。

**它已经是一个可在 Codex 中使用的独立仓库，但不是离开 Codex 就能自主完成营销研究和创意判断的独立视频引擎。** Agent 作为控制层是有意设计，不必因此重写成庞大的服务器。问题是控制层依赖的状态、契约与验证目前还不够硬。

`codexvideo create` 的作用主要是建立项目、选择路线、生成任务与契约；`resume` 报告下一阶段；`qa` 评估已有创意检查报告。它们不等价于一个已经封装好的 URL 到 MP4 全自动任务执行器。

### 三条主要路线没有共享完整策略

| 路线 | 当前阶段 | 差异 |
| --- | --- | --- |
| product-promo-factory | 17 阶段：事实、需求、用户任务、价值映射、Hook、brief、方案、生产契约、脚本、脚本检查、证据、连续性、Shotcraft、素材、编辑、合成、交付 | 营销方法最完整 |
| faceless-narrative | 8 阶段：研究、方案、脚本、分镜、素材、编辑、合成、交付 | 有需求研究和 Hook，但未强制复用完整痛点、证据、连续性流程 |
| ai-dialogue-podcast | 同样 8 阶段，增加 cast、dialogue 等产物 | 有角色与口型规则，但没有继承完整营销策略链 |

所以“选无脸/播客”当前不仅改变表现形式，还改变了前期制作流程。这是与目标最重要的架构偏差之一。

## 四、逐项完成度

评分锚点：0 为缺失；25 为说明或契约为主；50 为工具加人工串联样例；75 为大部分整合且有重复执行证据；100 为新环境可复现、关键故障可恢复、内容验收通过。各项是连续评分，不是机械套档。

| 能力 | 权重 | 完成度 | 已有能力 | 距离目标的主要差距 |
| --- | ---: | ---: | --- | --- |
| 产品事实与证据研究 | 6 | 65% | product_truth、proof_plan、网页捕获、证据引用 | 网站到实际结果的核实依赖 Agent；证据变动与失效未统一执行 |
| 消费者需求与排序 | 7 | 55% | pain_library、audience_job、排序工具 | 输入评分不等于真实搜索量；无跨项目验证过的需求数据闭环 |
| Hook 与前三秒 | 7 | 75% | 候选、评分、引用、时长检查规则 | 部分时长仍用词数估算；最终声音和首帧未统一绑定验收 |
| 英文脚本与 CTA | 7 | 70% | value_map、creative_brief、script、script_qa | 质量依赖当前 Agent，主线外形式未共享全部规则 |
| 无脸成片 | 10 | 60% | 旁白、素材、字幕、成片样例 | 真实结果镜头不足，容易回到大字卡片和网站截图 |
| 双人 AI 播客 | 10 | 40% | dialogue、cast、HeyGen 历史视频 | 后续版本退化为静态原型；角色、声音、口型与反应未形成稳定模板 |
| 镜头与整体质感 | 8 | 50% | Shotcraft 镜头库、多个渲染器 | 配方存在不等于成片采用；缺少可靠的视觉示范与审美验收 |
| 英文声音与声音设计 | 6 | 45% | TTS adapters、混音、字幕、历史配音 | 当前标准注册路径未就绪，样例依赖旁路；BGM/SFX 不是稳定默认产物 |
| 角色与场景连续性 | 5 | 55% | cast/continuity 契约与依赖声明 | 缺少通用失效传播和真实跨镜头一致性验证 |
| 现有素材剪辑与字幕 | 7 | 80% | 导入、缓存、转写接口、EDL、调色、切点 QA | 音轨选择未传到最终渲染；本地强制对齐尚未整合 |
| 技术与创意验收 | 6 | 55% | 解码、黑帧、静音、切点报告、创意评分 | 创意评分由外部填写，未与最终视频指纹强绑定，导出可绕过 |
| 批量变体与多比例 | 6 | 80% | campaign_batch、缓存、重试、多比例样例 | 8 变体已有证据；完整 6×3×2 高质量生产未验证，入口比例存在 bug |
| 恢复与依赖失效 | 5 | 40% | checkpoint、历史、局部缓存与批处理恢复 | failed 阶段恢复错误；通用 stale 状态和派生物校验不完整 |
| 开箱即用与引导 | 5 | 40% | create/doctor/CODEX_TASK、格式风格目录 | 干净环境未验证；ready 是计划就绪，安装与全局技能依赖不够清晰 |
| 费用、资源与权限 | 3 | 50% | CostTracker、预算契约、局部线程限制 | 未强制覆盖所有付费工具；无本次真实扣费核对，不能保证全局硬上限 |
| 导出与交付 | 2 | 85% | MP4、字幕、元数据、可编辑包、本地导出 | 不等于自动发 TikTok/YouTube；最终导出仍需统一验收绑定 |
| **合计** | **100** | **58.25/100** | **汇总表述约 60%** | **以目标体验而非文件数为分母** |

Hook 得分较高，只表示规则和工具比其他部分完整，不表示已证明高完播率。新用户与 SaaS 的定性判断是另外两个视角，不能与上述分数相加或平均。

其余较早的 faceless、pain-first、Shotcraft 样例也有本地文件；不能把不同日期、不同旁路生成的样例累加成一条当前统一且可恢复的生产线。

### 当前机器的可用性与依赖旁路

本次 registry 预检：TTS 0/10、视频生成 0/26、图像生成 0/16、avatar 0/4；本地后期、字幕、原片编辑路径较完整。这里的 0 是注册路径没有满足配置/运行条件，不是说源代码不存在，也不是说历史从未生成过。

最新产品片的音频元数据记录了 Kokoro / am_michael，但主工具注册中没有相应标准 adapter。历史音频可以存在，当前标准路径却不就绪：这是全局技能或外部制作路径没有被仓库完整封装的证据。没有输出或复制任何 API key 值。

### 为什么“总感觉效果发挥不出来”

1. 痛点文案已有改善，但展示产品结果的镜头不足。近期 VibeAha 和 NENE contact sheet 仍以大字、卡片、网页缩图为主。
2. 多个产品复用近似布局骨架，改变品牌颜色不等于建立适合产品的叙事与画面。
3. 模型生成的“相关画面”与产品真实结果不是同一种证据。前者能表达情境，不能证明产品功能。
4. 播客口型、反应、停顿和声音身份不是字幕与转场能补救的；静态头像方案天然达不到该目标。
5. 脚本、素材、视觉分别做了规则，最终却没有用同一条已渲染视频核对三者是否一致。

这不能推导出“这些技术不适合 SaaS”。更准确的结论是：目前过多强调描述产品和装饰文字，较少围绕用户得到的具体结果组织视频。也不能据此保证洗发水等实物品类一定更有效。

## 七、已确认缺陷与优先级

P1 表示影响主线正确性或严重误导就绪判断，应在下一次正式生产前处理；P2 表示需要纳入稳定性与产品化工作。以下都是待修，不是已修。

| 优先级 | 问题与定位 | 本次证据 | 后果与修复方向 |
| --- | --- | --- | --- |
| P1 | 音轨交接丢失：`tools/editing/raw_footage/render.py:521` | 构造 1 秒双音轨文件：track 0 静音、track 1 音调。ingest 正确选 1，峰值 -17.84 dBFS；真实 segment renderer 输出最大音量 -91 dB | 素材预检通过后成片仍可能无声；EDL 和 renderer 要显式继承每个 source 的音轨选择 |

## 八、建议的目标架构

不新增第二套通用编排框架，不急着建 SaaS，不把每个上游仓库整体复制一遍。保留 Codex 决策层和现有工具，先收敛为 **一套共同前期制作流程 + 三种表现形式 + 一套执行与验收机制**。

```text
共同前期制作
  product_truth -> pain_library -> audience_job -> hook_candidates
  -> creative_brief -> approved_script -> proof_plan
                         |
           +-------------+-------------+
           |             |             |
        faceless     product-proof    ai-podcast
     旁白+情境/结果   实录+结果+动效    角色+轮次+证据插入
           |             |             |
           +-------------+-------------+
                         |
共同执行与交付
  asset plan -> provider/cost approval -> media jobs -> timeline
  -> preview -> revision -> render -> artifact-bound QA
  -> accepted master -> controlled variants -> export -> metrics
```

“旁白/双人”是内容形式；“纪录片/干净产品/UGC”是风格；“痛点/对比/异议处理”是脚本结构；“FFmpeg/Remotion/HyperFrames”是渲染实现。四者不应混在一个 template 名字里，也不应改变消费者事实与证据。

### 应改动哪里，而不是再加多少目录

| 现有位置 | 建议调整 | 得到的能力 |
| --- | --- | --- |
| `codexvideo/catalog.py`、`project.py`、`cli.py` | 统一意图/比例解析，区分 planning/preview/render/delivery readiness；修复恢复 | 输入网站和内容形式后得到可信下一步 |
| `pipeline_defs/`、`skills/pipelines/` | 把共同营销产物作为三条路线的前置输入；减少重复策略说明 | 无脸、产品片、播客共享已经研究好的痛点、论点和证据 |
| `schemas/artifacts/` | 增量扩展现有 run_plan、asset、render、QA 契约，不为同一事实另造多份 JSON | 每次决定、素材、输出有唯一来源与明确版本 |
| `lib/checkpoint.py` | 强制产物集合、审批与依赖指纹；failed/stale 传播 | 改脚本后只重做必要音频/镜头，不继续交付旧视频 |
| `tools/base_tool.py` 及调用边界、CostTracker | 统一预算、调用幂等、provider receipt、取消和重试；避免静默切模型 | 可说明花了什么钱，失败不会盲目重新扣费 |
| `tools/editing/raw_footage/` | 音轨继承、不可覆盖 QA 历史、每边界检查 | 上传原片可剪辑，避免预检和成片不一致 |
| `tools/audio/`、avatar 相关工具 | 把成功配音旁路纳入正式 adapter；固定两位主持人的身份契约 | 新项目能重复使用相同声音和角色，失败明确停住 |
| `tools/analysis/`、`tools/publishers/export_bundle.py` | 技术检查+真实帧/音频检查+用户审批均绑定最终 render hash | 当前这条视频验收通过后才允许标正式交付 |
| `tests/`、安装配置、文档 | 三条标准样例、低成本 fixtures、无全局技能环境测试、文档契约检查 | 下载仓库后的承诺有自动回归证据 |

不需要先建 SQL 数据库才能管理痛点与脚本。当前 JSON schema + 项目目录足够；等需要跨项目检索、并发任务与真实投放指标查询时，再引入 SQLite 索引。数据库不能替代素材质量和运行契约。

## 九、按结果排序的优化与验收

### 第一阶段：修正主线正确性

先处理音轨、尺寸、failed 恢复、readiness、QA 指纹与不可覆写尝试记录。验收包括双音轨原片保留人声、三比例尺寸一致、failed/stale 绝不被跳过、换视频后旧 QA 不能继续通过、没有所需声音/角色来源时不显示 render-ready。

把本报告中的确定性复现加入回归测试。不要以“全套测试目前通过”代替这些新测试，也不要为了补齐记录给旧项目伪造已经通过的阶段。

### 第二阶段：同一产品，做出真正可复用的三条母版

选择一个自有产品，核实当前功能与实际结果。只做一个明确需求，以同一组真实证据完成三种形式：

| 母版 | 必须出现的证据 | 关键验收 |
| --- | --- | --- |
| 无脸旁白 | 情境画面、产品实际结果、需要时的操作片段 | 前三秒痛点清楚；音画逐句匹配；不是网页截图轮播 |
| 产品证明片 | 输入 -> 关键操作 -> 可见结果，必要时同条件对比 | 观众能看懂产品做了什么，而不仅是听到声称什么 |
| 双人播客 | 一个消费者疑问、一段解释、一个实际产品证据 | 两位角色稳定、动态口型、短轮次和反应自然；静态预览明确不能算正式成片 |

共同记录产品证据、脚本版本、声线、provider/model、耗时、费用来源、素材授权、最终文件 hash、QA 与用户意见。已经有有效授权的事项不重复询问；新的费用、身份、不可逆操作保留必要批准关卡。

本阶段目标不是拍出三条完全不同的技术演示，而是证明同一制作核心可以重复产出三种目标体验。

### 第三阶段：从好母版到批量和开箱使用

1. 先输出约 10 个针对不同需求的英文脚本，给出推荐 5 个的理由；区分需求证据与推测。
2. 选择母版后先做单变量测试，例如 2 Hook×固定主体×固定 CTA，而不是一开始做 36 个高成本版本。
3. 只有母版批准后才批量，多比例必须重新构图并检查字幕安全区，不能只缩放画面。
4. 中断后验证成功素材不重付费、失败任务能续跑；报告真实成本与人工干预步骤。
5. 在不依赖作者全局 skills、缓存或素材绝对路径的干净环境验证安装与最短制作旅程；macOS/Linux 做基线，Windows 单独验证后再承诺支持。
6. 用明确标识的演示素材提供无付费回归路径；演示成功不能冒充云生成验证。付费路径按已选供应商做独立、受批准的 smoke test。
7. 对外声明仅覆盖已验证路线与配置，先用指标导入建立 variant_id -> 成本/完播/点击/转化的记录，再做自动发布与平台连接器。

### 暂缓项

大规模引入新模型、3D 角色系统、本地换脸训练、自动社交账号登录、完整 SaaS 支付后台，以及继续增加不进入主线的 Skill 数量。它们不是没有价值，而是不能优先解决当前“作品不满意、工作流不稳定、新人跑不通”的问题。

## 十、当前可以和不可以对外承诺

可以：**CodexVideo 是在 Codex 中运行的本地 AI 视频制作工作台，提供消费者需求与脚本契约、可选媒体供应商、素材编辑、多种渲染路径、字幕、批量变体和本地交付工具。**

必须说明：生成质量依赖实际素材、脚本与所选供应商；部分格式需 API 配置、费用与人工审核；当前不保证所有路线在新环境零干预运行。

目前不应承诺：只填任意网站就必然得到精致且高转化的视频；两人播客已经稳定开箱可用；所有上游核心能力都已完整集成；全局绝不超预算或重复扣费；转化率自动优化；下载后不安装、不配置即可完成全部云生成。

**下一次可计入完成度的进展，应当是一条可复现、可恢复、可验收的好视频流程，而不是又多一个 API 或一份说明文件。**

## 审计限制

这是对关键用户旅程、核心模块、工具注册、代表性产物和测试的系统审计，不是对所有 vendored 源码逐行审查。本次没有测广告投放，没有重新听审全部配音，没有重新生成数字人，没有验证当前 API 余额或完成新机器安装，也没有核验所有上游版本与许可证的最新变化。未知事项保持未知。

本次只新增审计文档，未修改运行行为。现有代码缺陷、旧样例的契约不一致和各条优化建议均保留待办状态。
